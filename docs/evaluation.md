# How Bug Hunter is evaluated

A bug-finding tool is only as credible as its scorecard. This page defines what is measured, how, what the numbers can
and cannot claim, and how to compare Bug Hunter against another tool or a manual tester on equal terms. The current
numbers are in [BENCHMARKS.md](BENCHMARKS.md), generated by `scripts/benchmark.mjs`.

## Ground truth

Each benchmark target is an app whose defects are known in advance and can be switched on and off at runtime:

| Target | Domain | Seeded defects | What it tests |
|---|---|---|---|
| Demo shop (`src/DemoShop`) | E-commerce; visitors, shoppers, staff | 10: coupon stacking, expired card, non-positive quantity, case-sensitive search, overselling, tax truncation; order desk open to shoppers (permission), cancel after shipping (lifecycle), listed price differs from the cart (consistency), gift wrap per item (inside the gift-wrap feature) | Breadth: generic oracles and probes, then roles, lifecycles and cross-page checks |
| Demo Hotel (`src/DemoHotel`) | Bookings; guests, front desk | 8: past check-in, check-out not after check-in, over capacity, last night free; front desk open without sign-in (permission), cancel after check-in (lifecycle), charged rate above the quote (consistency), breakfast once (inside the breakfast feature) | Depth: business rules no generic oracle knows; only rules, roles and predictions can catch them |

Each app also ships:

- an **answer key** (`ground-truth/<app>/answer-key.json`): its roles, features, entities, lifecycles, endpoints,
  permissions, rules, journeys and seeded defects. Later phases score the twin, journeys and predictions against it. A
  test keeps each answer key's endpoints identical to the app's own OpenAPI document (`/openapi/v1.json`);
- **scenarios** (`ground-truth/<app>/scenarios/*.json`) for multi-run benchmarks: a baseline for run 1, then a sprint's
  changes (a story edited, a feature shipped with a bug in it, an unrelated regression, an earlier bug fixed), and
  what run 2 must report. `node scripts/scenario.mjs --app hotel --scenario sprint-2 baseline|apply|status` drives them;
- **feature switches** that change the app's surface between runs, and **versioned stories** edited by scenarios.

A defect that lives inside a feature (`requires` in the defect list) is left off by "every defect on" while its feature
is off, so it never counts as missed when it could not show.

Switching defects means the same build is scored with every defect on (**recall**) and every defect off (**false
positives**). Each hunt starts from a reset app (the setup hook), so runs are independent.

Scoring never relies on the hunter's own claims. For each seeded defect the engine has a predicate that inspects the
recorded HTTP response (`HuntEngine.Exhibits`): a finding is credited to a defect only if the response that triggered
it actually shows that defect. A broken rule must also be *about* the defect (it checks the defect's fields,
`HuntEngine.DefiningFields`): a capacity rule broken by a booking that also has past dates finds the capacity bug, not
the date bug. The hunter's oracles and rules never see these predicates or the defect switches.

## Metrics

| Metric | Definition | Why it matters |
|---|---|---|
| Found | Seeded defects with at least one credited finding | Raw recall |
| **Confirmed** | Seeded defects whose finding reproduced on 2 of 2 replays, without AI | What a team can act on without triage |
| **Unexplained** | Proven findings no seeded defect accounts for, from oracles and from AI-written rules, counted separately | With defects off, every one is a false positive, including a rule the engine itself flagged as probably wrong |
| Suspicions | Model opinions no check confirmed | Reported separately; never fail a build |
| AI cost | Tokens times list price, thinking included | The cost side of ROI |
| Model calls per confirmed bug | Model calls / confirmed seeded defects | How much AI a configuration needs for each proven bug |
| Minutes | Wall-clock time of the hunt, replays included | Fits in CI or not |

The headline is **confirmed recall at zero unexplained findings**. A tool that finds more but needs a human to discard
noise has moved the cost, not removed it.

## Controls

- **No-AI baseline.** Every app is also hunted by the Heuristic strategy (sweep, probes, built-in oracles, replay). AI
  configurations must beat it, and the gap is what the model is worth. On Demo Hotel the baseline is expected to find
  close to nothing, which is the point of that app.
- **Fixed inputs.** Every run of an app gets the same mission, stories, secrets, setup hook and step budget; probes and
  replay are on; repro shrinking is off (it changes time, not recall).
- **Budgets.** Every AI run is capped at $1.00; a run that hits the cap finishes without AI and is still scored.

## Threats to validity

Stated so readers can weigh the numbers correctly:

- **Author-seeded defects.** The defects were written by the same author as the hunter. Mitigations: the defects are
  ordinary, well-known bug classes; the hotel was built after the hunter's oracles were frozen; scoring is by response
  predicate, not by finding title. A third-party target (below) is the stronger test.
- **Small N and model variance.** A single run of an AI configuration is one sample. Rows are appended, not replaced,
  so repeated runs show spread. Treat differences of one defect between single runs as noise.
- **Skill packs.** `skills/*.md` give the planner domain knowledge (e-commerce, bookings). They describe bug classes of
  the domain, not the seeded defects, but they help. A run's report lists the skill packs it loaded.
- **Demo-sized apps.** Both targets are small. They measure whether the method works and what it costs, not how it
  scales to a large application.

## Head-to-head method

To compare Bug Hunter with another tool, an agent, or a manual tester:

1. **Same target, same state.** Use a demo app with every defect on, reset before each attempt
   (`POST /api/test/reset` with the admin key). For a false-positive pass, switch every defect off.
2. **Same information.** Give each contender the URL, the mission and the stories listed in `scripts/benchmark.mjs`,
   and the test account. No access to the source or the defect list.
3. **Same budget.** Fix wall-clock time (for example 20 minutes) and, for AI tools, the same AI budget.
4. **Score the same way.** A defect counts as found only if the contender's report gives steps that, run by a third
   person on a reset app, show the defect. Count reports that do not reproduce, or describe behaviour that is correct,
   as false positives.
5. **Report the full row:** found, reproduced, false positives, cost, time, and the human minutes spent triaging the
   report. That last number is where tools that report suspicions as bugs pay their bill.

To evaluate on your own application, seed two or three defects in a branch (an off-by-one in a total, a missing
validation), deploy it to a test environment with a reset endpoint, and run the same matrix. The `Exhibits` predicates
are the only app-specific scoring code; write one per seeded defect.
